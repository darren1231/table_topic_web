# 0002：AI 使用紀錄改為伺服器簽章，代幣以只能新增的帳本記錄

- 狀態：已接受
- 日期：2026-11-12
- 相關：[ADR 0001](0001-system-ai-key-without-service-role.md)

## 背景

ADR 0001 為了不使用 Supabase service role key，讓 `record_ai_usage` 以使用者本人的登入憑證呼叫。當時接受的風險是「使用者可以替自己多記帳」。

新增的打卡與代幣功能，規定「當天有一次成功的 AI 分析回饋才算打卡」，代幣又可以兌換 AI 額度。如果 `record_ai_usage` 維持使用者可直接呼叫，使用者就能假造一筆「AI 分析成功」的紀錄來打卡。

## 決策

1. **伺服器簽章**：Vercel Functions 持有一把簽章密碼（`USAGE_SIGNING_SECRET`），資料庫的私密表也存一份相同的密碼。
   - 伺服器每次呼叫 `record_ai_usage` 或兌換代幣時，附上 HMAC-SHA256 簽章、簽發時間與一次性 nonce。
   - 資料庫函式驗證簽章正確、時間在 5 分鐘內、nonce 沒用過，才寫入。
   - 使用者沒有這把密碼，無法假造紀錄。
   - 使用紀錄與兌換分別使用不同的固定簽章內容及 nonce 唯一索引；兌換有 `exchange|` 用途前綴。精確格式、數字／時間表示與錯誤碼見[實作計畫](../plans/2026-11-12-streak-tokens.md)。
2. **密碼存放**：資料庫內的密碼放在不對外公開的 `private` schema，資料表沒有任何 policy，只有 `security definer` 函式讀得到。Vercel 端放在環境變數。
3. **仍然不使用 service role key**。簽章密碼只能證明「這筆紀錄來自伺服器」，本身不授予資料庫存取權限；呼叫仍帶使用者的有效 JWT，由資料庫以 auth.uid() 綁定本人。
4. **代幣帳本**：每一筆代幣的增減都是 `token_ledger` 中的一列，只能新增，不能修改或刪除。餘額、連續天數都由帳本計算。修正以「新增一筆調整」完成，不改舊紀錄。
5. **規則放在資料庫函式**：打卡獎勵、漏簽扣點、補簽費用由資料庫函式計算，前端與伺服器都無法改變。只有兌換比例由伺服器的環境變數提供，並包含在簽章內容中。
6. **一天的界線**：一律使用 `Asia/Taipei` 的日期。
7. **交易與並行寫入**：同一使用者的打卡、補簽與兌換使用交易層 advisory lock，不對 Supabase 管理的 auth.users 取得列鎖；簽章記帳與打卡在同一交易內完成。餘額查詢包含確定會發生但尚未寫入的漏簽扣點，本身不寫入。
8. **補簽一致性**：補簽前以退回昨天實際扣點後的餘額判斷資格；今天已打卡時另記獎勵差額，使兩種順序得到相同結果。代幣增減以資料庫結果為準，前端僅依既定規則預覽明日獎勵。兌換比例可公開供確認，但實際兌換仍由伺服器取設定值並簽章。
9. **管理員唯讀摘要**：admin_list_tokens 使用與用量查詢相同的資料庫 email／已驗證判斷，不信任 JWT email；餘額含待扣點數，最後打卡日為成功 AI 分析打卡的日期。沒有後台寫入介面，也不授予使用者直接修改帳本的權限。

## 結果

- AI 使用紀錄與打卡都無法由使用者假造；後台的用量數字也更可信。
- 簽章密碼外洩的影響：搭配有效使用者憑證可偽造使用紀錄、打卡或兌換內容，增加 AI 支出；不因此取得其他使用者資料的讀寫權限。外洩時應一起更換 Vercel 與資料庫的密碼。
- 部署時必須同時設定 Vercel 環境變數與資料庫密碼，且兩者一致；不一致時所有記帳都會失敗。
- 密碼至少 32 個字元；Preview 與 Production 共用同一個 Supabase 專案，因此必須使用相同值。密碼缺少或不合法時，伺服器直接拒絕請求；兩端值不一致時，已產生的 AI 結果仍可回傳，但不會記帳或打卡。
- 執行新的 migration 後、新版伺服器部署前，舊版伺服器的記帳會失敗（AI 回覆仍會傳回）。部署時應盡快完成兩者。
- 新版伺服器先於 migration 部署時，舊版餘額回應沒有 bonus_credit，AI 請求會暫時失敗。上線順序及假值 SQL 範例見 [README](../../README.md#簽章密碼與部署順序)；migration 不包含密碼，也不會由 Vercel 自動執行。
