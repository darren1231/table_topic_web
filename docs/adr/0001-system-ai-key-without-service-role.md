# 0001：以系統 API key 取代自備金鑰，且不使用 Supabase service role key

- 狀態：已接受
- 日期：2026-11-08

## 背景

網站原本要求使用者自備 API key（BYOK），key 存在瀏覽器 localStorage。這對分會會員不友善，key 也可能因網頁漏洞外洩。

改由網站擁有者提供 key 後，費用由擁有者負擔，因此需要：

1. 每位使用者的花費上限。
2. 可信的使用紀錄，使用者不能自行刪改。
3. 讓管理員查看所有人用量的後台。

常見做法是讓伺服器持有 Supabase service role key，由伺服器寫入紀錄並讀取所有人的資料。

## 決策

- AI 呼叫改經 Vercel Function 代理，OpenAI key 只存在 Vercel 環境變數：Preview 環境使用 `CHATGPT_PREVIEW_KEY`，Production 環境使用 `CHATGPT_PRODUCTION_KEY`。
- 只有登入的使用者能使用系統 AI。每人額度 1 美元，不重置。
- **不使用 service role key。** 規則寫在資料庫的固定函式裡（`security definer`）：
  - 記帳函式只能替呼叫者本人新增一筆非負金額的紀錄，不能修改或刪除。
  - 查詢已用金額的函式只回傳呼叫者本人的金額。
  - 後台查詢函式先檢查呼叫者是否在資料庫內的管理員名單上，通過後才回傳所有人的紀錄，而且只能讀取。
- Vercel Function 以使用者本人的登入憑證呼叫上述函式。
- 管理員名單存放在資料庫，不放在 Vercel 環境變數。資料庫無法驗證外部伺服器宣稱「此人是管理員」，名單必須由資料庫自己判斷。

## 結果

- 沒有任何一把鑰匙外洩後能讀取或刪除所有使用者的資料。
- 使用者無法刪除或減少自己的已用金額，額度上限有效。
- 使用者可以直接呼叫記帳函式替自己多記帳，但只會減少自己的額度，不影響他人。
- 同一位使用者同時送出多個請求時，可能略微超過額度。
- 每個 Google 帳號都有額度，有人可以申請多個帳號來取得更多額度。目前以後台觀察因應。
- 資料庫函式必須仔細撰寫：固定 `search_path`、驗證輸入、限制文字長度，並以測試驗證。
- 自備金鑰的程式碼保留，只在介面上隱藏。
