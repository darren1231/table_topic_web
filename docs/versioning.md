# 版本管理與發布流程

本文件說明 Table Topic Practice 如何決定版本號、在哪裡記錄版本，以及發布新版本的步驟。版本內容見 [CHANGELOG.md](../CHANGELOG.md)。

## 版本號規則

採用[語意化版本](https://semver.org/lang/zh-TW/)：`主版號.次版號.修訂號`。

| 變更類型 | 調整哪一位 | 例子 |
| --- | --- | --- |
| 使用方式有重大改變，使用者或管理者必須重新學習或重新設定 | 主版號，例如 `2.0.0` → `3.0.0` | 改成登入才能使用 AI；資料格式改變且無法自動升級 |
| 新增功能，舊的用法照常可用 | 次版號，例如 `2.0.0` → `2.1.0` | 新增一種練習模式、新增一種語言 |
| 修正錯誤或小幅調整，不新增功能 | 修訂號，例如 `2.1.0` → `2.1.1` | 修正畫面錯誤、調整文字、安全性修補 |

只有測試、文件、CI 的變更，**不需要**發新版本，記在 CHANGELOG 的「尚未發布」，下次發布時一起列出。

## 版本號存在哪裡

發布新版本時，以下四個地方必須一致：

| 位置 | 內容 | 給誰看 |
| --- | --- | --- |
| `CHANGELOG.md` | 完整的版本紀錄：使用者變更、技術變更、升級注意事項 | 維護者、管理者 |
| `package.json` 的 `version` | 目前的版本號 | 開發工具 |
| `public/app.js` 的 `VERSION_HISTORY` | 精簡的使用者說明，顯示在網站「設定 → 版本紀錄」 | 使用者 |
| Git 標籤 `vX.Y.Z` | 指向發布時的 commit | 維護者 |

單元測試會檢查 `package.json`、`VERSION_HISTORY` 最新一筆與 `CHANGELOG.md` 最新的版本標題是否相同，不一致時 CI 會失敗。

## 平常怎麼記錄

每個會影響使用者或部署的 PR，都要在 `CHANGELOG.md` 的「尚未發布」段落加上一行：

- 使用者看得到的變更，寫在對應的分類：新增、調整、修正、安全性。
- 在「技術變更」表格加上 PR 編號與一句說明。
- 需要管理者手動設定的（例如新的 migration、新的環境變數），寫在「升級注意事項」。

寫法原則：

- 使用者變更用使用者聽得懂的話，說明「能做什麼」或「哪裡變了」，不寫程式細節。
- 公開 repo 中不寫尚未修正的安全漏洞細節。安全性修正只描述「加強了什麼」，不描述攻擊方式。

## 發布步驟

1. **決定版本號**：依上面的規則，看「尚未發布」裡最大的變更類型。
2. **開發布分支**：`release/vX.Y.Z`。
3. **更新四個位置**：
   - `CHANGELOG.md`：把「尚未發布」改成 `## X.Y.Z — YYYY-MM-DD`，補上標籤行，再新增一個空的「尚未發布」。
   - `package.json`：`version` 改成新版本號。
   - `public/app.js`：在 `VERSION_HISTORY` 最前面加一筆，寫 2–5 句使用者看得懂的說明。
   - `README.md`：如果功能或設定方式有改變，一併更新。
4. **開 PR**，等 GitHub Actions 的 `test`、`e2e` 都通過。必要時在 Preview 網址確認。
5. **合併 PR**。
6. **打標籤**：在合併後的 commit 上打附註標籤並推送。

   ```bash
   git switch main && git pull
   git tag -a vX.Y.Z -m "vX.Y.Z — 一句話摘要"
   git push origin vX.Y.Z
   ```

7. **建立 GitHub Release**：以標籤 `vX.Y.Z` 建立草稿，內容貼上 CHANGELOG 中這個版本的段落，確認後再發布。
8. **部署**：Vercel 會從 `main` 自動部署；發布前確認「升級注意事項」中的設定都已完成。

## 歷史標籤說明

- `v1.0.0` 指向 1.1.0 合併前的狀態，因為 1.0.0 的紀錄是在 1.1.0 時補記的。
- `v1.2.0`、`v1.2.1`、`v1.3.0` 是在同一次合併（PR #30）中發布，三個標籤指向同一個 commit。
- 1.4.0 曾寫在 CHANGELOG 中，但沒有在網站內公告，也沒有打標籤，內容已併入 2.0.0。
